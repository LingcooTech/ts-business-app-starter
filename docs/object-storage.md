# Object Storage

Stage 6 adds provider-neutral object storage with two runtime adapters:

- `local`: Node.js file-system storage for development and single-host deployments;
- `s3`: the official AWS SDK v3 against AWS S3 or an S3-compatible endpoint such as Cloudflare R2,
  MinIO, DigitalOcean Spaces, or Qiniu Kodo.

The application owns `ObjectStoragePort`, authorization rules, metadata, audit, and Admin workflows.
It does not reimplement an S3 client or expose provider credentials to Controllers or browsers.
Additional native providers such as Google Cloud Storage or Azure Blob can be added as adapters
without changing the public HTTP contract.

The S3 adapter intentionally uses the official AWS SDK v3 and presigner packages rather than a
custom transport or signature implementation. The provider-neutral port remains application-owned,
so native provider SDKs can be added later without coupling Controllers to any one vendor.

## Upload flow

1. An authenticated caller requests upload authorization with filename, MIME type, byte size,
   visibility, and an allowed logical prefix.
2. The server validates limits and generates the final object key. User filenames never become paths.
3. A `pending` metadata row is created in `storage_objects`.
4. Local storage returns an authenticated multipart API URL whose lifetime is enforced by the API.
   S3 returns a short-lived presigned PUT URL generated by `@aws-sdk/s3-request-presigner`.
5. Local upload completion is atomic through a temporary file and rename. S3 completion performs a
   provider HEAD request.
6. The server verifies size and MIME metadata before changing the row to `ready`. Mismatched provider
   objects are deleted rather than accepted.

The API never returns access keys or secret keys. S3 credentials are read from encrypted Settings or
environment fallbacks and may be omitted when the official SDK credential chain is available.

## Access and deletion

Public local objects use `/api/storage/public/:id`. Private local objects require `storage.read` and
use `/api/storage/objects/:id/content`. S3 objects use either a configured public/CDN base URL or a
short-lived signed GET URL.

Deletion first removes the provider object, then marks metadata `deleted`. Upload authorization,
ready completion, deletion, and connection tests are recorded in append-only Audit logs.

## Security policy

- `STORAGE_MAX_UPLOAD_BYTES` limits declared and completed object size;
- `STORAGE_ALLOWED_MIME_TYPES` supports exact types and wildcards such as `image/*`;
- `STORAGE_ALLOWED_PREFIXES` restricts logical ownership roots;
- upload and private access URLs have configurable short lifetimes;
- local paths are resolved beneath `STORAGE_LOCAL_ROOT` and reject traversal;
- Docker runs as a non-root user and mounts a dedicated writable storage volume while the remaining
  container filesystem stays read-only.

Content-type metadata is validated, but it is not a malware scanner or full magic-byte inspection.
Applications accepting untrusted executable documents should add antivirus/content inspection before
making objects available.

## Operations

Local storage is the safe default and persists in the `storage_data` Compose volume. It is suitable
for development and a single Docker host. Multi-host or independently scaled API deployments should
use S3-compatible storage so every replica sees the same objects.

Important settings and environment fallbacks:

- `storage.provider` / `STORAGE_PROVIDER`;
- `storage.s3-region` / `STORAGE_S3_REGION`;
- `storage.s3-endpoint` / `STORAGE_S3_ENDPOINT`;
- `storage.s3-bucket` / `STORAGE_S3_BUCKET`;
- `storage.s3-access-key` / `STORAGE_S3_ACCESS_KEY`;
- `storage.s3-secret-key` / `STORAGE_S3_SECRET_KEY`;
- `storage.s3-force-path-style` / `STORAGE_S3_FORCE_PATH_STYLE`;
- `storage.public-base-url` / `STORAGE_PUBLIC_BASE_URL`.

For Qiniu Kodo, configure its S3-compatible endpoint, region, bucket, and credentials. For MinIO,
configure the endpoint and normally enable path-style addressing.
